  # 1. Концептуализация области знаний "Управление контекстом внимания ИИ-Агентов на базе LLM"

  ## 1.1 Архитектурный подход
  Мы вводим фундаментальное разделение ответственности для масштабируемости мультиагентных систем (Separation of Concerns).
  
  ### Слой Знаний (Knowledge Layer)
  *   **Роль:** Методолог / Дизайнер Контекста (The Methodologist).
  *   **Задача:** Творческая, исследовательская работа. Изобретение и формализация фреймворков, методологий и "знаний" с чистого листа. Это качественная работа.
  *   **Артефакт:** "Унитарный Промпт" или "Модуль Знаний" (`Prompt Module`). Это текстовый файл (YAML/Markdown), который содержит саму суть методологии.
  *   **Процесс:** Промпт-инжиниринг.
  
  ### Слой Оркестрации (Orchestration Layer)
  *   **Роль:** Архитектор / Оркестратор Системы (The System Architect).
  *   **Задача:** Инженерная, структурирующая работа. Не изобретает методологии, а берет готовые "модули знаний" и строит из них надежный бизнес-процесс. Это количественная работа и управление сложностью.
  *   **Артефакт:** Код сервиса-оркестратора и DCL-скрипты.
  *   **Процесс:** Контекст-инжиниринг (Операционный).
  
  ### 1.2 Ролевая модель (Separation of Concerns)

  Мы выделяем два принципиально разных слоя работы с когнитивными системами:

  #### Роль 1: Методолог / Дизайнер Контекста (Knowledge Layer)
  *   **_Суть_:** Творческая, исследовательская работа по формализации знаний.
  *   **Задача:** "С чистого листа" изобретать, формализовывать и описывать фреймворки, методологии и знания. Создание `Prompt Modules` (статичных артефактов).
  *   **Результат:** Унитарный Промпт или Модуль Знаний в Библиотеке (например, `lenses/collector.yaml`).
  *   **Процесс:** "Промпт-инжиниринг" в строгом смысле.

  #### Роль 2: Архитектор / Оркестратор Системы (Orchestration Layer)
  *   **_Суть_:** Инженерная, структурирующая работа. Управление сложностью.
  *   **Задача:** Не изобретать методологии, а брать готовые "модули знаний", созданные Методологом, и строить из них надежный бизнес-процесс с помощью DCL.
  *   **Результат:** Код сервиса-оркестратора и DCL-скрипты.
  *   **Процесс:** "Сборка Контекста" и "Управление Сессией".
  
  ## 1.3 Онтологическая модель. Иерархия Контекстов (The Context Hierarchy Ontology)

  Мы рассматриваем контекст LLM-based Агента как иерархическую многоуровневую систему вложенных сущностей, определяющую универсальную концепцию `Контекст`. Таким образом определение достигает охвата и конкртеизации на всей прикладных уровнях от отдельного элемента инструкции LLM до всего рабочего процесса, реализуемого мультиагентной системой.
  
  ### Уровень 1: Context Frame (Контекст Интенции/Намерения)
  *   **Определение:** Семантически завершенный, переиспользуемый модуль инструкции или данных (YAML-файл). Является дизайн-тайм артефактом.
  *   **Структура:** "Разреженный объект" (Sparse Object) с 7 инвариантными секциями (`identity`, `strategy`, `guardrails`, `knowledge`, `interface`, `output`, `verification`).
  *   **Ответственность:** Методолог.
  *   **Соответствие типовым GenAI API:** `genai.types.Part` (физический уровень) / Логическая группа Part'ов. |
  
  ### Уровень 2: Invocation Context (Контекст Вызова)
  *   **Определение:** Полная совокупность информации для одного-единственного вызова к LLM API.
  *   **Состав:** Динамически собранный System Prompt (из модулей) + Инструменты (MCP) + Входные данные.
  *   **Ответственность:** Оркестратор (автоматическая сборка по DCL-команде).
  *   **Соответствие типовым GenAI API:** В `genai` - совокупность параметров `generate_content` (`contents`, `system_instruction`, `tools`).
  
  ### Уровень 3: Session Context (Сессионный Контекст)
  *   **Определение:** Stateful-объект в Agentic Runtime (AR), хранящий состояние одной многошаговой DCL-операции.
  *   **Состав:** История всех вызовов (chain), промежуточные артефакты (черновики), метаданные (бюджет токенов), результаты вызова инструментов.
  *   **Ответственность:** Agentic Runtime.
  *   **Соответствие типовым GenAI API:** В `genai` - cовокупность параметров `generate_content` (`contents`, `system_instruction`, `tools`).
  
  ### Уровень 4: Workflow Context (Контекст Процесса)
  *   **Определение:** Высокоуровневое состояние долгоживущего бизнес-процесса (BPMN).
  *   **Состав:** Только ключевые бизнес-данные (`itemId`, `status`, `approval_flag`). Не содержит "мыслей" агента.
  *   **Ответственность:** Workflow Engine.
  *   **Соответсвие:** `Process Instance Variables` в Workflow Engine.


  # 2. Фундаментальная Концепция DCL (Domain Context Language)

  ## Определение и Назначение
  см. рабочие артефакты в C:\git\dcl\dcl-core, C:\git\dcl\dcl-god-mode
  
  DCL — это декларативный, высокоуровневый язык, который служит промежуточным слоем между бизнес-логикой приложения и исполнительным механизмом ИИ-агентов. Его основная задача — транслировать абстрактное бизнес-намерение в конкретную, структурированную и воспроизводимую инструкцию для ИИ-оркестратора.

  DCL не заменяет низкоуровневые протоколы (как MCP), а управляет ими. Это язык для оркестрации целого воркфлоу или бизнес-задачи, которая может состоять из нескольких вызовов LLM, использования инструментов и логического ветвления.

  ## Сравнение DCL и MCP (Model Context Protocol)
  Мы строго разграничиваем эти понятия:

  | Критерий | Model Context Protocol (MCP) | Domain Context Language (DCL) |
  | :--- | :--- | :--- |
  | **Уровень Абстракции** | **Низкоуровневый / Исполнительный.** Описывает *конкретный инструмент* (`get_schema`, `save_file`). Аналог TCP/IP или CLI команд. | **Высокоуровневый / Стратегический.** Описывает *бизнес-процесс* (`REFINE Schema`, `GENERATE Narrative`). Аналог HTTP или скрипта оркестрации. |
  | **Драйвер Процесса** | **Модель.** Модель решает, какой инструмент вызвать и когда. Приложение реагирует на запрос модели. | **Приложение / Оркестратор.** Оркестратор решает, какой бизнес-процесс запустить и по какой стратегии. Модель — один из инструментов. |
  | **"Интеллект"** | В **модели**. Модель должна догадаться по контексту, что ей нужно вызвать инструмент. | В **Оркестраторе и Библиотеке Контекстов**. Оркестратор знает стратегию выполнения (шаги A, B, C). |
  | **Область Действия** | **Один "шаг"**. Обычно используется для получения фактов или выполнения простых действий. | **Целый воркфлоу.** Описывает многошаговую бизнес-операцию. |

  ### Архитектура Интеграции: BPMN + Agentic Runtime (AR)
  Для реализации DCL в Enterprise-среде применяется архитектура "Когнитивного BPMN":
  
  1.  **BPMN Engine:** Управляет стратегическим бизнес-процессом. Использует `Agent Task` (реализованный как Service Task), чтобы делегировать когнитивную работу. Он управляет `Workflow Context` (бизнес-переменные).
  2.  **Agentic Runtime (AR):** Специализированная среда ("Когнитивное Ядро"), которая получает DCL-команду от BPMN. Она управляет `Session Context`, стохастикой, ретраями и цепочками вызовов LLM.
  3.  **MCP:** Используется внутри AR как тактический протокол для взаимодействия LLM с внешним миром в рамках одного шага.

  ### DCL vs. Model Context Protocol (MCP)
  Это разные уровни абстракции. DCL не дублирует MCP, а является семантическим слоем поверх него.
  
  *   **DCL (Domain Context Language):**
      *   **Уровень:** Высокоуровневый / Стратегический. Описывает целый воркфлоу или бизнес-задачу.
      *   **Драйвер:** Приложение / Оркестратор.
      *   **Аналогия:** HTTP (семантика запроса: GET/POST).
      *   **Пример:** "Улучши схему для категории Книги, используя Линзу Коллекционера".
  
  *   **MCP (Model Context Protocol):**
      *   **Уровень:** Низкоуровневый / Тактический. Описывает конкретный инструмент и протокол обмена данными в рамках одного шага.
      *   **Драйвер:** Модель (LLM решает, какой инструмент вызвать).
      *   **Аналогия:** TCP/IP (транспорт пакетов).
      *   **Пример:** "Вызвать функцию `get_schema_details(id='books')`".

   ### Альтернативы построения Онтологии мета-домена Domain Context Language (Rationale).Варианты концептуализации
  *   **Таксономическая модель (Entity-Oriented Decomposition (Subject-Verb-Object))**:
  *   *   _Суть_: "все есть Сущность" оказалась громоздкой. Дл.ВCL, каы языка операционализации контекста, более уместны другие подходы.
  *   *   Критерий: Группировка вокруг ключевых сущностей языка.
  *   *   Структура: DCL_Entities (Определения Модулей и Операндов), DCL_Verbs (Каталог Операторов и их логика), DCL_Qualities (Модификаторы, Линзы, Цели).
  *   *   Статус: [**ОПРОБОВАН**, **ОТКЛОНЕН**] см. *DCL: Research DCL God Mode* по результатам оценки артефакта - слишком громоздко и искусственно формально.
  *   **Алгебраический подход (Category Theory based):**
  *   *   _Суть_: Рассматривать DCL как алгебру, где ContextFrame — это объекты, а Operators — это морфизмы (стрелки), трансформирующие один контекст в другой.
  *   *   Плюсы: Идеально для описания рекурсии и композиции.
